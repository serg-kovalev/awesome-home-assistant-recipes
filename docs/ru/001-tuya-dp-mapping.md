# Карта точек данных «неподдерживаемого» Tuya-устройства

[English version](../en/001-tuya-dp-mapping.md)

*Создано: 2026-08-14*

## Симптом

В официальной интеграции Tuya устройство отображается как `Heat Recovery Ventilator (unsupported)`.
Сущностей — ноль. В диагностике интеграции видно, почему:

```json
"category": "xfj",
"status": [{"code": "switch", "value": false}],
"local_strategy": {
  "1": {"status_code": "switch", "config_item": {"valueType": "Boolean"}}
}
```

1 точка данных. При этом приложение SmartLife для того же прибора показывает 3 режима
проветривания, 3 скорости, ночной режим, 3 режима влажности и 2 датчика.

`unsupported` здесь означает не «сломано», а «в базе нет профиля для этой модели». Но важнее другое:
**облачная схема устройства урезана самим производителем**. Определять по ней нечего — точек в ней
действительно 1.

Вывод, который стоит сделать сразу: если приложение умеет больше, чем облачный API, копать надо
**локально**, а не в облаке.

## Что понадобится

- `local_key` устройства — берётся через Tuya IoT Platform;
- [`tinytuya`](https://github.com/jasonacox/tinytuya);
- сетевая доступность до устройства по TCP/6668 (см. [рецепт 2](002-iot-network-segment.md)).

## Шаг 1. Получить local_key

1. На [iot.tuya.com](https://iot.tuya.com) создать облачный проект. **Data Center выбирать тот же,
   что у вашего аккаунта** — иначе список устройств придёт пустым. Определить его можно по endpoint
   в диагностике интеграции Tuya: `apigw.tuyaeu.com` → Central Europe.
2. В проекте: **Devices → Link App Account** → отсканировать QR в SmartLife.
3. Со вкладки Overview взять `Access ID` и `Access Secret`.

Дальше в отдельном каталоге:

```bash
python3 -m venv venv
./venv/bin/pip install tinytuya
./venv/bin/python -m tinytuya wizard
```

Мастер спросит `Access ID`, `Access Secret`, ID любого устройства и регион (`eu`), а затем сложит
рядом `devices.json` с ключами всех устройств аккаунта.

> **Если `pip install tinytuya` падает на сборке `cryptography`** с требованием Rust — не ставьте
> Rust. У tinytuya есть альтернативный криптобэкенд:
>
> ```bash
> ./venv/bin/pip install --no-deps tinytuya
> ./venv/bin/pip install requests colorama pycryptodome
> ```
>
> Жалоба pip на отсутствующую зависимость `cryptography` останется, но работать будет.

После этого `tinytuya.json` (в нём лежит `Access Secret`) можно удалить: для локальной работы нужен
только `devices.json`.

## Шаг 2. Снять полный список DP

```bash
./venv/bin/python -m tinytuya scan
```

Обычный скан ловит устройства по их широковещательным объявлениям. Если устройство в другой подсети —
оно не найдётся, и это нормально, см. [рецепт 2](002-iot-network-segment.md). Прицельно, по подсети:

```bash
./venv/bin/python -m tinytuya scan -force 192.168.30.0/24
```

`-force` работает только когда `devices.json` с ключами уже на месте.

Результат — то, ради чего всё затевалось:

```
DPS: {'1': False, '101': False, '102': False, '103': False, '104': False,
      '105': False, '106': False, '107': False, '108': 311, '109': 331,
      '111': False, '112': False, '113': False}
```

13 точек против 1 в облаке.

## Шаг 3. Понять, что означает каждая точка

Значения ничего не скажут: 11 `False` выглядят одинаково. Нужен эксперимент — переключать
по одному элементу в приложении и смотреть, какая точка изменилась.

Опрашивать вручную утомительно, поэтому используйте
[`watch_dp.py`](https://github.com/serg-kovalev/awesome-home-assistant-recipes/blob/main/examples/tools/watch_dp.py) — он опрашивает устройство раз в 2 секунды и
печатает **только изменения**:

```
[12:02:38] СТАРТ: {"1": false, "101": false, ..., "108": 309, "109": 281}
[12:03:41] DP 1: False -> True
[12:03:43] DP 113: False -> True
[12:03:45] DP 101: False -> True
```

Методика:

1. Запустить наблюдатель.
2. Переключить **одну** вещь в приложении.
3. Пауза 5 секунд — чтобы состояние попало в отдельный снимок.
4. Повторить для каждого элемента управления.

3 вещи, которые сэкономят вам час:

**Пауза обязательна.** Опрос идёт раз в 2 секунды. Без паузы 2 действия сольются в один снимок, и
вы не поймёте, какое из них что переключило.

**Числовые точки дрейфуют сами.** Датчики шумят на единицу и засоряют лог. Фильтруйте их при чтении,
а масштаб определяйте сравнением с приложением: `389` при показаниях `38.9 %` означает множитель 0.1.

**Не доверяйте облачному журналу событий.** На iot.tuya.com в Device Logs видны имена точек
(`Speed one`, `Humidity Two`, `Sleep Mode`) — соблазн сопоставить их по времени велик. Не делайте
этого: между событием `Publish` (команда из приложения) и `Report` (подтверждение прибора) там
проходит до минуты, и сопоставление по времени даёт ложные пары. Я так «доказал», что одна и та же
точка отвечает и за вторую скорость, и за второй режим влажности.

Надёжный способ — писать значения самому и смотреть, что подсветилось в приложении. Приложение здесь
выступает словарём имён:

```python
import tinytuya
dev = tinytuya.Device("<DEVICE_ID>", "192.168.30.16", "<LOCAL_KEY>", version=3.4)
dev.set_value(104, True)   # что загорелось в приложении?
```

## Что получилось

| DP | Назначение | Тип |
|---|---|---|
| 1 | питание | bool |
| 101, 102, 103 | скорость low / medium / high | bool, взаимоисключающие |
| 104 | ночной режим | bool |
| 105, 106, 107 | порог влажности low / medium / high | bool, взаимоисключающие |
| 108 | влажность, ×10 | int |
| 109 | температура, ×10 | int |
| 111, 112, 113 | приток / вытяжка / рекуперация | bool, взаимоисключающие |

## Прошивочные странности, которые стоит поискать и у себя

Разбирая карту, я наткнулся на 4 поведения, которых нет ни в одной документации. Проверьте
аналогичные у своего прибора — они определяют, как писать интеграцию.

**Точка, которая игнорирует `False`.** Запись `105 = False` не даёт ничего: ошибки нет, ответ
приходит, значение остаётся `True`. Выключить контроль влажности можно только повторной отправкой
активного режима проветривания (`113 = True`, когда он и так `True`). То есть обычный переключатель
на такую точку не годится — нужен обходной сценарий.

**Повторная запись — не пустая операция.** Отправка уже установленного значения имеет побочный
эффект: именно так и сбрасывается влажность. Отсюда практическое правило: **не подтверждайте
состояние без нужды**. Если прибор уже включён, не посылайте «включить» ещё раз — вы не знаете, что
именно прошивка сделает с этим повторным подтверждением.

**Задержка отчёта.** После записи устройство может 5 и более секунд отдавать старое значение.
Дважды приняв это за «команда не сработала», я чуть не выкинул рабочее решение. Проверяйте
результат с задержкой не меньше 10 секунд.

**Команды режимов игнорируются при выключенном питании.** Прибор молча отбрасывает переключение
режима, если `DP 1 = False`. Это придётся учесть в сценариях: сначала питание, пауза, потом режим.
